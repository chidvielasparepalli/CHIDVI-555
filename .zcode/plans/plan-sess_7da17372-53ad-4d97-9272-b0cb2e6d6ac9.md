## Step 2: Create AnimationManager module (NEW file)

**New file:** `web/src/animation-manager.js`

This is a self-contained ES module with no side effects. It exports a class and a function.

### Architecture

```
AnimationManager
├── animationCache: Map<string, AnimationClip[]>    // URL → clips
├── mixer: THREE.AnimationMixer | null               // reference to currentMixer
├── currentAction: THREE.AnimationAction | null      // currently playing clip action
├── idleAction: THREE.AnimationAction | null          // looping idle
├── queue: string[]                                    // queued animation names
├── isPlayingFBX: boolean                             // flag for procedural conflict
├── crossFadeDuration: number                         // seconds (default 0.35)
├── state                    // one of: idle, playing, transitioning
├── onPlaybackComplete: callback | null               // called when non-idle finishes
├── onAnimationChanged: callback | null              // called on any clip change
```

### Key Methods

- **`bindMixer(mixer)`** — attach to the existing `currentMixer`. Called after each avatar switch. Clears all cached actions.
- **`loadAnimation(url): Promise<AnimationClip[]>`** — loads an FBX via FBXLoader, caches result, returns clips. Skips if already cached.
- **`preload(urls)`** — preload multiple animations (for startup).
- **`play(name, options?)`** — plays a named animation. Options: `{loop, crossFadeDuration, afterPlay}`. Stops current non-idle, cross-fades to new clip. When done, auto-returns to idle unless `afterPlay` is set.
- **`playIdle(name?)`** — starts a looping idle animation. Default: `idle.fbx`.
- **`playGesture(name, afterPlay?)`** — plays a one-shot gesture, then returns to idle.
- **`queueAnimation(name)`** — adds to queue; plays next when current finishes.
- **`clearQueue()`** — empties the queue.
- **`stop()`** — fades out current, returns to idle.
- **`isFBXActive(): boolean`** — returns whether an FBX clip is currently driving the skeleton (used by procedural system to know when to back off).
- **`dispose()`** — cleans up all actions, cache, references.

### Cross-fade Logic

Uses `THREE.AnimationAction.crossFadeTo()` + `warp` or manual weight interpolation. Standard approach:
1. Create new action from clip: `mixer.clipAction(clip)`
2. Set `newAction.setEffectiveWeight(0)`, `.play()`, `.crossFadeTo(currentAction, duration, warpTrue)`
3. Fade out old action weight to 0
4. When old action reaches weight ~0, stop it

### Queue Logic

When a non-idle animation finishes (`finished` event fires), check the queue. If items exist, pop and play. Otherwise, return to idle.

### Procedural animation gating (modify `applyProceduralPose`)

Add a check at the top of `applyProceduralPose(t, delta)`:
```js
if (animManager.isFBXActive()) return
```

This prevents procedural bone rotation from fighting FBX animation clips. The expression system, blink system, and mouth system remain active (they use blend shapes, not bones).

### Modify `applyActionPose` to route through AnimationManager

When `performAvatarAction` is called with a recognized animation name (wave, nod, clap, etc.), route to `animManager.playGesture()` instead of procedural bone animation. For unrecognized actions (look_left, look_right, etc.) that have no FBX, keep the existing procedural system.

Updated `performAvatarAction` logic:
```js
window.performAvatarAction = (action) => {
    const a = String(action || "").toLowerCase()
    // Try FBX animation first
    if (animManager.hasAnimation(a)) {
        animManager.playGesture(a)
        return
    }
    // Fall back to procedural for unrecognized actions
    activeAction = a
    actionStartedAt = clock.elapsedTime
    // ... existing emotion-setting logic for smile/laugh/thinking/greeting
}
```

### State change integration (modify `applyEmotionTarget`)

When `setAvatarState` or `setAvatarEmotion` is called with a state that maps to an animation, trigger the corresponding animation:

```js
function applyEmotionTarget(emotion) {
    avatarEmotion = String(emotion || "idle").toLowerCase()
    resetEmotionTargets()
    const values = emotionExpressions[avatarEmotion] || emotionExpressions.idle
    for (const [name, value] of Object.entries(values)) {
        setExpressionTarget(name, value)
    }
    // Trigger state-based animation
    animManager.onStateChange(avatarEmotion)
}
```

## Step 4: Add `playAnimation` bridge to Python (ui.py)

### Add new signal in `MainWindow.__init__` (after line 1238)

```python
_animation_sig = pyqtSignal(str, dict)  # name, options
```

Connect it (after line 1315):
```python
self._animation_sig.connect(self._play_animation)
```

### Add slot method (after `_perform_avatar_action`)

```python
def _play_animation(self, name: str, options: dict = None):
    if hasattr(self.hud, "page"):
        safe_name = json.dumps(name)
        safe_opts = json.dumps(options or {})
        self.hud.page().runJavaScript(
            f"window.playAnimation && window.playAnimation({safe_name}, {safe_opts});"
        )
```

### Add public method on `JarvisUI` class

```python
def play_animation(self, name: str, options: dict = None):
    self._win._animation_sig.emit(name, options or {})
```

This adds one new bridge point. No existing signals, slots, or methods are modified. Personality, Gemini, speech, and avatar switching code are untouched.

## Step 5: No changes to main.py for Phases 1-5

State mapping (Phase 3) is handled entirely in the JS layer: when `window.setAvatarState("listening")` is called, the `applyEmotionTarget` function triggers `animManager.onStateChange("listening")` which plays `breathing_idle.fbx`. This means the existing state change pipeline (`main.py` → `ui.py` → JS `setAvatarState`) already drives animation transitions with zero changes to main.py.

Gesture commands (Phase 4) flow through the existing `performAvatarAction` bridge — same command router, same action string, just routed to FBX instead of procedural bones.

Emotion animations (Phase 5) can be triggered later by adding emotion detection to Gemini responses or user text parsing — that will be a future enhancement that simply calls the existing `window.playAnimation` bridge.
